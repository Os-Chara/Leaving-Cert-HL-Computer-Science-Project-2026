Design Objectives:


The goal of this project is to design a forest monitoring system made up of an embedded system and a Python model which completes all the following objectives.

  • Operate as a tree-mounted embedded monitoring device.
  • Monitor temperature, humidity, and soil moisture using external sensors.
  • Be able to store the collected environmental data and run basic preprocessing.
  • Have a simple model programmed locally on the embedded system to calculate the wildfire risk.
  • Adapt automatically to changing environmental conditions and update wildfire risk at regular intervals.
  • Include a Python program on a computer that can take the preprocessed data and run further modelling and visualisation of data.
  • Allow patterns and trends in wildfire risk over time to be identified.

Stakeholders and End User Needs:


This device’s primary stakeholders will be forest monitoring organisations. They require accurate and reliable environmental data and methods for predicting high-risk conditions. Monitoring an entire forest requires many devices distributed throughout the environment, so minimising the cost per unit is essential. Manually collecting the data from all these devices would be infeasible, so wirelessly transmitting this to their computers is essential. Many forests are vast in size, limiting the response times of these organisations to risks, so an automatic warning system will be needed.

Options to meet Design Objectives:


Option 1: Micro:Bit based system
This design would use Micro:Bit to process sensor inputs and control the outputs, based on a simple local model.

Pros:

  • Simple to program due to MakeCodes block-based programming language [11].
  • Crocodile clip connectors along with a built in LED display make testing and bug fixing easy.
  • Built in radio communication modules would make transmitting the data to the computer for modelling simple [12].

Cons:

  • Limited storage capabilities of 256KB would make storing large continuous datasets impractical [13].
  • Only 16KB of RAM are available, which would limit the complexity and speed of the local model [13].
  • Limited voltage output of 1.7V-3.6V [14].
  • Requires a breakout board for solid wiring, which uses up a lot of space.
  • Higher price point at €19.95 [15].


Option 2: Raspberry Pi Pico W based system
This design would make use of a Raspberry Pi Pico W for processing the inputs from the sensors, which would then be used to run a simple local model which would determine the outputs.

Pros:

  • Greater storage capabilities of 2MB make continuous, large datasets more practical [16].
  • The 264KB of RAM allows faster processing and more complex local models [16].
  • Multiple voltage outputs from 1.8V-5.5V, allow for a wider variety of hardware options [17].
  • The Pico W’s built in Bluetooth and Wi-Fi chip would allow for the wireless transfer of data from the Pico to the computer for modelling [18], albeit more complex than the radio modules on the Micro:Bit.
  • Low cost at only €4-6.

Cons:

  • No built in LED display means more external hardware is required if displaying information or debugging is required.
  • Requires MicroPython which is more complex than block programming.

These two options were compared under the following criteria:

Features Micro:Bit Raspberry Pi Pico W
Programming Complexity Low Medium
Storage 256KB 2MB
RAM 16KB 264KB
Cost €19.95 €6
Difficulty of Debugging Low Medium
Wireless transmission Radio modules Bluetooth and Wi-Fi chip
Available Voltages 1.7V-3.6V 1.8V-5.5V

Based on this comparison, I chose the Raspberry Pi Pico for my final design. Despite the Micro:bit’s ease of programming and debugging, its limited storage and processing power make it an impractical choice for continuous monitoring and data processing. The Pico compensates for its greater overall complexity with significantly larger memory capacity, greater processing power, and a wider voltage range, while also being available at a lower cost. These advantages make it the most suitable platform for this project.

Technologies:


Along with the Pico W the following hardware and software will be used.

Thonny: This Python IDE is ideal for programming both the model and the Pico. Its simple UI and built-in support for MicroPython make it easy to develop and test code. It also allows the Pico to print output directly to the shell through a serial connection, making debugging more convenient.
Notepad++: A lightweight text editor used for creating the HTML and CSS files for my website, with features such as syntax highlighting that improve readability.
Fusion 360: Free CAD software that will be used for designing an enclosure for the system components.
Capacitive Soil Moisture Sensor: Outputs the soil moisture level as an analogue value. Unlike resistive sensors with exposed metal probes, capacitive sensors avoid corrosion making them more long-lasting and sustainable.
DHT22: This is a cheap and easy to use digital temperature and air humidity sensor. Pre-made MicroPython libraries and higher accuracy over the DHT11 make it suitable for this project.
Pico OLED 1.3 Display: This device is designed specifically to compensate for the Pico’s lack of built in display. Pre-made libraries allow it to easily display live sensor data.
Active Buzzer: Active buzzers contain an internal oscillator unlike passive buzzers, meaning programming them is as simple as just supplying voltage. This makes them perfect for the alarm system.
Red LED: This will add to the system’s alarm feature, red is associated with danger and would stand out in a green forest environment.
